# Техническое задание: UX/UI-аудит и переработка admin UI

## 1. Цель и границы

Подготовить существующую административную страницу к презентационному
редизайну, не меняя бизнес-логику админ API, хранения данных и AI-процессов.
В реализации требуется:

1. Перенести **все** CSS из `admin.html`, включая CSS для HTML, собираемого
   JavaScript во время работы, в модульный SCSS.
2. Настроить настоящую Sass-компиляцию с отдельными командами build и watch.
   Скомпилированный CSS хранить в проекте и отдавать через FastAPI.
3. Сохранить возможность обычного запуска приложения на Python без Node.js,
   npm или Sass-компиляции во время запуска.
4. Переработать UX/UI, сохранив бизнес-функции страницы и обе темы.
5. Улучшить семантику, клавиатурное управление и доступность; адаптивность,
   контрастность и поведение при `prefers-reduced-motion` проверить для обеих
   тем.

Это спецификация, а не реализация. На этапе аудита изменён только этот файл;
исходники и тесты не редактировались. Реализацию не начинать в рамках данного
этапа.

### Не входит в задачу

- Изменение методов, URL, авторизации, форматов запросов/ответов и бизнес-правил
  `app/admin.py` и связанных сервисов.
- Изменение БД, схем, AI-поведения, Telegram-бота или состава пользовательских
  данных.
- Изменение JS-поведения, кроме минимальных, заранее согласованных изменений,
  необходимых для презентации и доступности.
- Утверждение новых API-контрактов или появление новых административных функций
  без отдельного согласования.
- Чтение `.env`, файлов или содержимого `data/`, SQLite и запуск приложения с
  локальными секретами/данными.

## 3. Подтверждённая карта стилей и проблем

### Исходное распределение CSS

В `admin.html` весь текущий CSS расположен в одном встроенном блоке
`<style>` — строки **7-351**:

- строки **8-245**: базовые переменные, оформление страницы, заголовки,
  masthead, панели, сетки, prompt-карточки, trace drawer, формы, кнопки,
  таблицы, статус и прочие общие компоненты;
- строки **246-334**: тема `data-theme="kawaii"` — фон, текст, панели,
  формы, кнопки, трассировка и таблицы;
- строки **335-347**: адаптивные правила для ширин до 600 и 700 px;
- строки **348-350**: обработка `prefers-reduced-motion`.

JS генерирует HTML с классами, которые используют правила из того же блока:
например, `.row`, `.danger`, `.prompt-card`, `.placeholder-list` и
`#users .row` (генерация/вставка: `admin.html:539-546`, `587-593`,
`607-611`, `647-668`, `792-800`, `867-875`, `902-918`; определения:
`admin.html:140-228` и `647-668`). Они также должны быть покрыты SCSS и
скомпилированным CSS, а не только статически видимой разметкой.

### Найденные UX/UI и технические проблемы

1. **Нет модульного стиля и отдельной компиляции.** Вся тема и компоненты
   находятся в единственном `<style>` (`admin.html:7-351`). В репозитории на
   момент аудита не найдено SCSS/CSS-исходников, Sass build/watch-команд или
   frontend package manifest. `requirements.txt:1-10` содержит только
   Python-зависимости; `start.command:23-56,117-154` готовит Python venv,
   запускает Uvicorn и бота, не выполняя frontend-сборку.
2. **Остались динамические inline-стили.** `admin.html:795` и `:873`
   вставляют атрибут `style="max-width: min(100%, 360px); height: auto;"`
   изображениям, созданным шаблонными строками JS. Оба стиля перенести в
   общий CSS-класс; не оставлять динамические `style=` как исключение.
3. **Навигационные landmarks отсутствуют.** Документ имеет `header` и
   отдельные `section`, но в `admin.html:353-463` нет `main` и `nav`.
   Требуются логичная навигация/иерархия разделов и переход к основному
   содержимому. Не переименовывать используемые JS `id` без согласования.
4. **У полей не везде есть доступные имена.** Связанные метки уже есть для
   токена (`admin.html:373-374`) и тестового пользователя (`:400-401`).
   Поля provider/API key не имеют явной label-связи (`:442-447`); в шаблоне
   маршрутов provider/model/max_tokens генерируются без меток
   (`:587-592`); общие системные textarea создаются без меток
   (`:673-680`). Нужно проверить и маркировать все статические и динамические
   поля, сохраняя селекторы и API.
5. **Фокус частично решён, требуется сохранить и проверить обе темы.** Явное
   правило фокуса сейчас есть (`admin.html:210-213`), но его видимость,
   контраст и отсутствие обрезания при редизайне не проверялись в браузере.
   Состояния `hover` недостаточно для клавиатурных пользователей.
6. **Асинхронные состояния почти не представлены.** Нет обнаруженных
   индикаторов загрузки и `aria-busy` для сетевых контейнеров. `#status`
   имеет `role="status"` (`admin.html:378`), ошибки prompt-test получают
   локальный `role="alert"` (`:804-808`), однако результаты других async
   операций и пустые/загружаемые состояния не имеют системной модели
   live-announcement. Сохранять единое ненавязчивое сообщение о загрузке,
   успехе и ошибке без повторяющихся объявлений.
7. **Trace drawer не задаёт диалоговый фокус-контракт.** Это `aside` с
   `hidden` (`admin.html:426-432`); открытие/закрытие реализованы через
   `.hidden` (`:811-818`). В исходнике не обнаружены `dialog`/`aria-modal`,
   перевод и возврат фокуса, закрытие по Escape. При необходимости
   улучшения согласовать структуру/минимальный JS отдельно.
8. **Есть предупреждение о несохранённом prompt, но нет сохранения
   черновика.** `admin.html:691-707` сравнивает textarea с активной версией и
   предупреждает `beforeunload`, но черновик не сериализуется. В браузерном
   хранилище записываются только токен (`sessionStorage`, `:465-466,508-516`)
   и тема (`localStorage`, `:475-488`). Нужно обеспечить восстановление
   текстового черновика после перезагрузки вкладки без подмены активного
   prompt.
9. **Адаптивность узкая и не проверена на реальных viewport.** Имеются
   `max-width: 600px` и `700px` (`admin.html:335-347`); необходимо проверить
   все формы, таблицы, длинные значения, панели и drawer от 320 px до широкого
   desktop, включая масштабирование/увеличение текста.
10. **Бизнес-функция планов не совпадает с видимой страницей.** Backend
    объявляет маршруты планов (`app/admin.py:162-243,245-287`), а README
    говорит об истории/повторной отправке планов (`README.md:61-63`), но
    текущий `admin.html` не вызывает plan endpoints. Это подтверждённое
    расхождение описания и текущего браузерного кода; само наличие маршрута
    не доказывает наличие плановой UI. Не добавлять её в редизайн как
    подразумеваемое требование — получить отдельное решение о включении.

- изменение AI-маршрутов и бюджета, просмотр расхода (`:585-621`);
- изменение системных prompt, история версий, четыре prompt-карточки
  диагностики/заданий и вставка разрешённых placeholder (`:623-751`);
- просмотр персонального контекста и privacy note, prompt-тест, результат,
  изображение, trace, принятие/отклонение варианта (`:753-860`);
- просмотр AI-логов, хранение/отображение ключа провайдера через API,
  просмотр/удаление изображений и content-cache, просмотр vector templates
  (`:861-935`).

Важные зафиксированные сервером правила:

- prompt test отправляет текущее содержимое редактора и профиль, но сам по
  себе не активирует новый prompt; активная версия заменяется только
  отдельным `PUT /admin/settings/prompts/{name}` (`app/admin.py:313-327`,
  `341-478`).

- API-логи раскрывают сохранённые зашифрованные запрос/ответ только через
  защищённый маршрут (`app/admin.py:581-597`).

Не менять тексты подтверждения опасных действий, область удаления,
приватность, разделение общих/персональных данных и смысл состояния
`pending`/`accepted`/`rejected`.

## 6. Целевая Sass/FastAPI-архитектура

Предлагаемая структура (окончательные имена файлов согласовать до реализации):

```text
scss/
  admin.scss                 # entrypoint
  _tokens.scss               # CSS custom properties / дизайн-токены
  _base.scss                 # reset, типографика, landmarks
  _layout.scss               # сетки и responsive layout
  _components.scss           # формы, панели, таблицы, drawer, prompt cards
  _themes.scss               # dark + kawaii
  _accessibility.scss        # focus, reduced motion, visually-hidden
app/
  static/
    admin.css                # скомпилированный и закоммиченный runtime asset
```

Точные partials могут быть объединены/разделены по согласованию, но проект
должен использовать Sass-модули `@use`/`@forward` (не создавать одну копию
неразделённого текущего блока). В SCSS должно быть единое место определения
токенов двух тем; обе темы остаются переключаемыми через существующий
`data-theme`, если не согласовано иначе.

- Добавить отдельную frontend build-конфигурацию с закреплённой версией
  Dart Sass (`sass`) и lock-файлом. Предусмотреть документированные команды
  `build` и `watch`, например `npm run build:css` и `npm run watch:css`.
- Build компилирует SCSS в `app/static/admin.css`; включить CSS без зависимости
  обычного запуска от source map/SCSS-файлов. Компилятор не вызывать из
  `start.command`, при импорте `app.admin`, старте Uvicorn или из
  `requirements.txt`.
- Скомпилированный `admin.css` является runtime-файлом проекта и должен

- Добавить в HTML `<link rel="stylesheet">` на предложенный статический URL,

  относительно `app/admin.py`, а не относительно текущего рабочего каталога.

- Отсутствие скомпилированного файла не должно вызывать запуск npm/Sass или
  ломать импорт/обычный старт приложения; запрос CSS может дать ясный 404,
  страница должна деградировать в неоформленную, но рабочую HTML/API страницу.

  200. Не выдавать пустой ответ или случайно иной asset вместо актуального.
- Watch нужен только разработчику. Проверить, что после Sass build в CSS

## 8. UX и accessibility-требования

### Семантика, метки, клавиатура и фокус

- Использовать логичную последовательность `header`, доступную навигацию по
  основным секциям, skip-link и один `main`; структура заголовков начинается
  с одного `h1`, секции имеют описательные `h2`, вложенные карточки —
  соответствующие подзаголовки. Семантическая навигация не должна ломать
  существующие `id`/селекторы.
- У каждого input/select/textarea есть видимая label, связанная `for`/`id`
  или семантически эквивалентная обёртка. Это включает статические поля и
  динамические маршруты, общий prompt, provider/API key, поиск по Telegram ID
  и тестового пользователя. Placeholder не заменяет label.
- Все действия доступны с клавиатуры в логичном tab order; никакое действие
  не зависит от наведения указателя. Отображать чёткий `:focus-visible` с
  достаточной толщиной/отступом и контрастом в обеих темах; не убирать
  стандартный outline без равноценной замены. Проверить zoom 200-400%.
- Тема переключается клавиатурой; `aria-pressed` и accessible name
  соответствуют текущему действию/теме и не теряют смысл при смене текста.
- Если drawer остаётся overlay-панелью, согласованно решить семантику,
  перемещение фокуса, возврат к триггеру, закрытие Escape и доступность
  закрывающей кнопки. Не оставлять клавиатурный фокус в скрытом содержимом.

### Статусы, ошибки и черновики

- Сетевые действия (вход/списки, сохранение, тест генерации, загрузка логов и
  кэша) показывают понятное состояние загрузки, успеха или ошибки. Для
  асинхронных контейнеров использовать корректный `aria-busy`; сообщения
  объявлять через подходящие `role=status`/`aria-live="polite"` и
  `role=alert` для важных ошибок. Не делать каждый прогресс шумным live
  сообщением; сообщения не должны исчезать до того, как их можно прочитать.
- Не отображать потенциально устаревшие данные так, будто загрузка прошла
  успешно. При отказе API сохранять понятную ошибку, а не молча оставлять
  пустой блок.
- Сохранять prompt-черновики локально в контексте вкладки, чтобы перезагрузка
  не теряла ввод; рекомендуемый механизм — `sessionStorage`, отдельный ключ
  на prompt. Черновик никогда автоматически не становится активным, не
  отправляется в AI/на сервер и не заменяет версию без явного тестирования или
  подтверждённого «Сохранить и заменить». Успешное сохранение обновляет
  исходную версию и очищает соответствующий локальный черновик. Учитывать
  невалидный/недоступный storage без падения редактора. Текущий
  `beforeunload`-guard можно сохранить как дополнительную защиту.
- Не сохранять локально значения API key или профильные/AI данные ради
  презентационного состояния. Существующее хранение токена и темы не
  расширять без отдельного решения.

### Motion, контраст и адаптивность

- Сохранить `prefers-reduced-motion: reduce` для всех новых transition,
  animation и smooth-scroll эффектов; режим не должен зависеть от темы.
- Обе темы сохраняют назначение и различимость статусов, ошибок, disabled,
  hover и focus. Проверить цвет текста/фона, placeholder, кнопки, границы,
  focus ring, таблицы и ошибки. Целевой минимум WCAG AA: 4.5:1 для обычного
  текста, 3:1 для крупного текста и значимых UI-графических границ/состояний,
  где применимо. Текущие измерения в разделе 3 — только исходные контрольные
  пары, не готовая приёмка.
- Проверить viewport не шире 320 px, 375/390 px, пороги 600/700 px,
  планшетный и широкий desktop, portrait/landscape, увеличение текста и
  длинный локализованный контент. Не допускать горизонтального переполнения
  всей страницы; длинные JSON/таблицы могут иметь локальную прокрутку,
  контролы должны оставаться доступными.
- Уважать минимум комфортный размер интерактивных целей и расстояние между
  кнопками, не прятать важные действия, избегать плотной сетки на телефоне.

# Отдельное ТЗ: запуск одной иконкой и защищённый удалённый доступ

## 1. Цель, границы и исходные ограничения

На втором ноутбуке оператор запускает бота и админку одной иконкой; при
первом запуске получает понятную настройку и подготовку необходимых
зависимостей, при следующих — контролируемый запуск. Удалённый администратор
открывает постоянную HTTPS-ссылку обычным браузером, без установки программ на
своём устройстве. Серверный ноутбук при этом включён и подключён к интернету.
Без предварительной настройки домена и внешней учётной записи это не работает.

Это ТЗ, а не реализация. При исследовании и проверках **не** менять настоящие
`.env`, базы данных, действующие процессы, пользовательские файлы и сервисы;
не публиковать данные, не поднимать интернет-туннель и не отправлять код,
секреты или данные пользователей третьим сторонам. Существующее рабочее дерево
содержит изменения и новые файлы, в том числе документы прошлых задач: не
откатывать, не перезаписывать и не форматировать их попутно.

Для будущей реализации в scope: логика запуска и безопасной настройки,
проверка доступа, управление процессами, тесты и адресное дополнение
документации. Текущий локальный режим должен оставаться доступным и совместимым.
Не менять бизнес-логику бота, схему БД или действующие API без обоснованной
необходимости. `admin.html` и SCSS **не требуют изменений** для этого варианта:
страница уже использует same-origin URL и существующий пароль; обмен и
пояснения можно организовать в лаунчере и инструкции. Изменения UI допустимы
лишь по отдельно подтверждённой необходимости и не являются обязательными.

Сейчас подтверждён только macOS-лаунчер `start.command`, которому нужен
предустановленный Python 3.11+. ОС второго ноутбука неизвестна: нельзя обещать
одинаковую иконку или установку для Windows/Linux без их подтверждения и
проверенной отдельной реализации. Иконка может открывать окно терминала;
терминал остаётся открытым, пока работают процессы. Без установки программ
требуется работать **администратору в браузере**, не обязательно хосту.

  Время изменения выбранных релевантных файлов совпадает с manifest графа;
  признаков последующего изменения этих исходников не обнаружено, поэтому
  обновление не запускалось. `start.command` отсутствует в manifest графа:
  отсутствие ребра запуска не означает отсутствия связи, его поведение
  установлено непосредственным чтением файла. Граф и другие артефакты не

- `start.command:23–56` проверяет версию Python, при отсутствии `.env`

- `start.command:117–174` запускает Uvicorn на `127.0.0.1:8000`, ждёт

- `app/admin.py:52–94,126–149`, `app/security.py:27–30`: приложение

  пароль приложения. В UI/API есть персональные и чувствительные данные;
  защита одного API при открытой HTML/CSS не равна защите всего origin.

## 3. Целевая архитектура и fail-closed

Предпочтительный вариант — **именованный Cloudflare Tunnel + Cloudflare
Access**, только после ручной настройки владельцем и явного согласия на
обработку трафика Cloudflare. Анонимный quick tunnel и любая автоматическая
публикация без Access категорически исключены; отказ настройки не должен
переключать систему на публичный режим без защиты.

Планируемый поток, не существующий пока в коде:

1. Администратор → HTTPS-имя в своём домене → Cloudflare Access с
   авторизацией только явно разрешённых администраторов → именованный tunnel
   → локальный защитный reverse-proxy → существующий FastAPI loopback origin.
   Прокси должен защищать **все** пути, включая `/admin`, `/static/`,
   `/health`, API и неизвестные пути, а не только отдельный endpoint.
2. Прокси на каждом запросе проверяет подписанный Access JWT assertion:
   доверенный issuer конкретной организации, ожидаемый audience конкретного
   приложения, допустимые алгоритмы и подпись через доверенные ключи,
   срок действия/`nbf`, а также остальные обязательные условия выбранного
   профиля валидации. Не доверять клиентским заголовкам идентичности.
   Отсутствие, подмена, истечение, неизвестный ключ или недоступность
   достоверных ключей без безопасного актуального кэша → отказ. Политика
   обновления ключей/кэша должна быть ограничена по времени и проверена;
   неподтверждённое или устаревшее состояние не открывает доступ.
3. Сохранить отдельный локальный origin для прежнего запуска на loopback;
   tunnel направляется **только** на защищённый proxy, не напрямую на
   Uvicorn. Ни один слушатель не привязывается к внешнему интерфейсу. Сам по
   себе loopback не защищает от других локальных пользователей/процессов:
   безопасность хоста и отсутствие ненадёжных локальных аккаунтов — условие.
4. JWT подтверждает выданное утверждение, но не доказывает корректность
   действующей Access-политики. Перед удалённым запуском и периодически во
   время работы нужна авторитетная проверка текущей конфигурации через
   ограниченные read-only полномочия Cloudflare либо иной проверяемый
   механизм: точный hostname/приложение/audience и маршрут tunnel → proxy,
   Access применяется ко всем путям, только согласованные администраторы,
   нет обходящих/BYPASS, публичных или более приоритетных альтернативных
   правил/приложений и незащищённых ingress-маршрутов. Проверять и режим
   конфигурации tunnel (локальный или управляемый удалённо), не только
   локальный файл. При неопределённости, ошибке API, недостатке полномочий,
   изменении политики или после ограниченного интервала без успешной
   повторной проверки — закрыть proxy и остановить tunnel, не выдавать
   ссылку как защищённую. Конкретный поддерживаемый Cloudflare API, права,
   полнота проверки и интервал контроля должны быть доказаны реализацией;
   пока это требование, не подтверждённый контракт. Если надёжно доказать
   защиту нельзя, удалённый режим недоступен.
5. Access и проверка JWT — дополнительный слой, не замена `ADMIN_TOKEN`.
   Не передавать пароль, tunnel credential, API token или другие секреты в
   URL, логи, список аргументов процесса, граф или сообщения об ошибках.
   Учитывать существующее хранение токена в `sessionStorage` и риск XSS,
   общего браузера и украденной сессии.

Первая настройка с пошаговыми инструкциями: создать/выбрать Cloudflare
организацию и подконтрольный домен, настроить именованный tunnel и DNS,
Access application и явную политику, получить нужные ограниченные полномочия
для проверок, задать фиксированное имя и доверенные параметры, проверить
маршрут. Не считать аккаунт, домен, политику и сертификаты уже созданными.
Автоматическая загрузка `cloudflared` на хост — только при необходимости,
из официального источника с проверкой подлинности/целостности и совместимости
архитектуры; предпочтительно использовать имеющийся проверенный бинарник.
Не устанавливать системные пакеты и не требовать прав администратора ОС без
необходимости. Ошибки сети, pip, Python и cloudflared объяснять с действиями
по исправлению. Инструкции не должны предлагать небезопасные обходы.

Это не обещание, что данные никогда не проходят через третью сторону: при
включённом удалённом режиме HTTPS-трафик обрабатывается Cloudflare; нужно
отдельное согласие, проверка договорных/правовых условий и настроек хранения
логов, сессий и обработки чувствительных данных. При компрометации аккаунта,
домена, хоста, токена или браузера защита может быть обойдена. Нужны MFA для
администраторов Access, отзыв доступа/учётных данных, ограничение срока
сессии и процедура ротации. Уже выданные assertion могут оставаться пригодны
до истечения; требование немедленного отзыва требует отдельного решения и
проверки. Отказ Cloudflare/сети означает отсутствие удалённого доступа, а не
отключение защиты.

## 4. Процессы и пользовательский сценарий

- Явно различать локальный и удалённый режим; отсутствие настроенного Access
  не ломает существующий локальный запуск и не создаёт публичный адрес.
  Выбор режима и первая настройка — понятные и воспроизводимые; последующий
  запуск одной иконкой не требует повторного ручного ввода неизменившихся
  параметров, если это безопасно и пользователь ранее согласился.
- Проверять prerequisites и конфигурацию до побочных действий. Существующие
  `.env`, ключ шифрования и БД не перезаписывать, не мигрировать и не
  заменять; не генерировать новый ключ для существующих зашифрованных
  данных. При нехватке безопасной конфигурации остановиться с объяснением.
  Размещение и права новых секретов и файлов состояния должны быть
  ограничены владельцем; не затирать существующие пользовательские файлы.
- Проверить свободные порты/одиночный экземпляр без убийства чужих
  процессов; при конфликте остановиться с ясной диагностикой. Не считать
  чужой ответ `/health` готовностью своего процесса. Проверять живучесть и
  готовность соответствующих дочерних процессов; отличать «процесс запущен»
  от подтверждённого подключения Telegram и защищённой доступности извне.
- Порядок: проверка настроек и зависимостей → собственный admin origin и
  проверка готовности → бот и честный статус → в удалённом режиме защитный
  proxy, проверка политики и маршрута → named tunnel → ссылка только при
  доказанной защищённости. Таймауты ограничены; секреты не попадают в вывод.
  Нет подтверждения каждого условия — нет сообщения «защищённая ссылка
  готова». Автооткрытие браузера — только после соответствующей проверки.
- Контролировать admin, bot, proxy и tunnel; при аварии любой обязательной
  части закрыть удалённый доступ и остановить принадлежащие лаунчеру
  процессы, сообщить причину. Ctrl+C/закрытие штатным способом и неуспех
  промежуточного старта выполняют ограниченный graceful shutdown с fallback
  только для своих дочерних процессов. Никаких `killall`/остановок чужих
  сервисов. Предусмотреть повторный запуск после сбоя.

## 5. Контракты, модули и модели

Подтверждённые текущие контракты: `GET /health` → `{"status":"ok"}`;
`GET /admin` → HTML; `GET /static/admin.css` → CSS или 404 при отсутствии
файла; для защищённых маршрутов, например `GET /admin/users`, требуется
проверяемый приложением токен, неверный/отсутствующий → 401. Существующие
форматы бизнес-API и Pydantic-модели (`app/schemas.py`) не меняются.
Текущая конфигурация `Settings.from_env()` включает `TELEGRAM_TOKEN`,
`ADMIN_TOKEN`, `DATA_ENCRYPTION_KEY`, `DATABASE_PATH` и другие параметры;
новый сетевой контракт или переменные окружения пока **не существуют**.

Предлагаемые внутренние данные конфигурации: режим, HTTPS hostname,
идентификатор организации/issuer, audience приложения, идентификатор tunnel,
путь к защищённым credentials, параметры локального proxy и срок действия
проверенного состояния политики. Их имена, формат и безопасное хранение
определить в реализации; это не существующая модель/API. Токены и ключи не
включать в публичную конфигурацию и тестовые отчёты.

Затрагиваемые компоненты будущей работы: `start.command` или выделенный
тестируемый модуль лаунчера; новый локальный Access-validating proxy и код
проверки Cloudflare-конфигурации; при необходимости небольшой слой
конфигурации; `README.md`/отдельная инструкция, тесты `unittest` и
изоляционные фикстуры. Изменение `app/admin.py` не обязательно при отдельном
proxy; если понадобится — сохранять локальные контракты. Поставка Python и
cloudflared на хост, способ проверки integrity и протокол безопасного
первичного ввода требуют проектного решения. Node/npm для runtime не нужны.

## 6. Критерии приёмки

1. На подтверждённой macOS и чистом изолированном тестовом экземпляре
   двойной щелчок по поставляемой иконке приводит к настройке зависимостей,
   понятной первой настройке и запуску; повторный запуск работает без
   повторной настройки при неизменных параметрах. Ограничения Python и ОС
   явно изложены; поддержка другой ОС не заявлена без проверки.
2. Прежний локальный сценарий и существующие API/UI функционируют; реальная
   конфигурация, база и прочие пользовательские файлы не затронуты при
   разработке и тестировании. Занятый порт и повторный запуск не приводят
   к остановке чужого процесса или ложной готовности.
3. Публичный hostname — только именованный tunnel, только HTTPS и только
   после проверки защищённого маршрута и соответствующей Access-политики.
   Отсутствующие/ошибочные credentials, недоступная проверка или её
   устаревание, bypass, неверный hostname/audience/маршрут, упавшие процессы
   или недоступные доверенные ключи не приводят к открытию доступа. Quick
   tunnel и запасной анонимный режим отсутствуют.
4. Невошедший, неразрешённый или подделавший заголовки клиент не получает
   HTML, CSS, health, API или ответов origin; только разрешённый пользователь
   с действительной Access-сессией проходит proxy, а защищённые API ещё
   требуют действующий `ADMIN_TOKEN`. Прямого внешнего доступа к origin нет.
   Проверка проделана для методов и путей, а не только корневой страницы.
5. Ссылка не содержит секретов, вывод не раскрывает их; информативные
   состояния и ошибки различают локальную готовность, бот, Access и tunnel.
   При остановке/сбое закрывается внешний доступ и корректно завершаются
   только собственные процессы. Инструкция описывает prerequisites, защиту,
   восстановление, MFA, ротацию, отзыв, угрозы и ответственность Cloudflare.

## 7. План проверок без воздействия на настоящие сервисы

- Изолированные временные каталоги, синтетические секреты и тестовая SQLite;

  ошибки установки/скачивания/проверки целостности, испорченные параметры,

- Проверить правильные и отсутствующие/истёкшие/неверные JWT, issuer,

- Смоделировать Access policy drift, bypass, пересечение маршрутов,
  несоответствие remote-managed tunnel, нехватку прав, сбой и устаревание
  повторной проверки: tunnel/proxy закрываются, ссылка не рекламируется.

  таймаут, Ctrl+C, очистку только собственных процессов и отсутствие
  секретов в логах.
- Регрессионно выполнить существующий `python -m unittest discover -s tests
  -v` и относящиеся тесты UI в безопасной изоляции; не считать их запуск
  выполненным в рамках исследования. Реальный end-to-end Cloudflare-тест
  возможен только отдельно, в специально выделенных аккаунте/домене и с
  синтетическими данными, после явного разрешения владельца; до него
  удалённая работоспособность и конфигурация не подтверждены.

## 9. Продолжение ТЗ: обязательная проверка Cloudflare Access JWT на origin

Это продолжение предыдущего раздела о запуске и удалённом доступе, а не
замена его требований и не отчёт о готовой реализации. Цель продолжения —
добавить проверяемую защиту самого ASGI origin: в явно включённом remote mode
каждый запрос должен предъявлять подлинное утверждение Cloudflare Access и
принадлежать отдельному локальному allowlist email. Настройка/выдача JWT не
заменяет действующий `ADMIN_TOKEN`.

### 9.1. Основание и подтверждённое состояние

- По исходникам `app/admin.py` создаёт FastAPI через `create_app()`.
  `GET /health`, `GET /admin` и `GET /static/admin.css` сейчас доступны без
  `ADMIN_TOKEN`; бизнес-маршруты используют зависимость `authorize()`.
  `authorize()` извлекает Bearer из заголовка `Authorization` и вызывает
  `valid_admin_token()` из `app/security.py`; последняя сравнивает токены
  через `hmac.compare_digest`. В исходниках нет проверки Access JWT,

### 9.2. Границы этой работы и несмешиваемые доказательства

1. Требуется реализовать строгую локальную проверку Access assertion в
   `app.admin`/ASGI слое, а не полагаться на то, что запрос пришёл через
   «правильный» proxy. В remote mode она должна защищать origin даже если
   запрос доставлен напрямую другим ingress/named tunnel, обходящим
   предусмотренный reverse proxy. Access JWT нельзя считать доказательством,
   что запрос прошёл через конкретный tunnel.
2. Эта проверка доказывает только то, что конкретное утверждение подписано
   доверенным Access issuer, относится к ожидаемому приложению и содержит
   разрешённую личность согласно локальному allowlist. Она **не** доказывает,
   что в аккаунте включена правильная эффективная Access policy, что все
   hostname/path защищены, что отсутствуют bypass/приоритетные правила,
   что задан нужный ingress, что tunnel принадлежит владельцу домена или что
   конфигурация не изменилась после проверки.
3. Предыдущий раздел 3, пункт 4 и его критерий 6.3 — авторитетная проверка
   всей текущей Cloudflare Access policy, hostname, bypass/конфликтов и
   фактической конфигурации tunnel — остаются отдельным невыполненным
   требованием. Их нельзя помечать выполненными на основании успешной
   проверки JWT, ручной настройки, наличия tunnel credential, UI-галочки,
   локального issuer/audience либо успешной загрузки JWKS. Если отдельная
   полная проверка policy не реализована, remote запуск всё ещё должен
   оставаться недоступным согласно предыдущему критерию.
4. Не входит: автоматическое создание/получение Cloudflare account,
   покупка/регистрация домена, включение Access/IdP/MFA, получение права
   владения доменом, создание политики с внешними побочными эффектами,
   публикация production-сервиса и проверка реального пользовательского
   трафика. Эти действия требуют владельца, его явного согласия и отдельной
   первичной настройки.
5. Для этой задачи не нужен презентационный UI или новая веб-страница
   управления Access. Требуются логика проверки origin и безопасная
   текстовая настройка/диагностика в существующем лаунчере. Небольшие
   терминальные инструкции и скрытый ввод секрета — функциональная настройка,
   не презентационный редизайн админки. Сам `/admin` в remote mode защищён
   middleware, а уже после Access пользователь по-прежнему вводит
   `ADMIN_TOKEN` для административных API.

### 9.3. Место enforcement, режимы и локальный health

- Ввести явное, серверное и fail-closed различение local/remote mode.
  Режим не выбирается по HTTP-заголовку, cookie или forwarded header.
  Невалидная/неполная remote-конфигурация должна остановить запуск remote
  app до принятия запросов; запрещено незаметно откатываться к незакрытому
  приложению или локальному режиму, доступному из внешнего ingress.
- В remote mode предпочтителен ASGI middleware в `app.admin.create_app()`,
  установленный до маршрутизации и исполняемый для всех HTTP методов и всех
  путей, включая `/admin`, `/static/admin.css`, `/health`, API,
  неизвестный маршрут и ошибки/404. Не делать исключений для GET, CSS,
  health, OPTIONS, корня, «внутреннего» URL-префикса, `Host`, IP клиента
  или forwarded-заголовков. Если появятся WebSocket/другие ASGI типы,
  они должны быть запрещены либо иметь равноценную проверку; не допускать
  альтернативный незащищённый протокол.
- Сохранить существующий `authorize()` и `ADMIN_TOKEN`: JWT gate
  дополняет их, но не удаляет и не подменяет. Для API чтения/изменения
  `ADMIN_TOKEN` по-прежнему обязателен. Страница/CSS/health в remote mode
  также требуют Access middleware, даже если на локальном запуске они
  остаются доступны без Access. Недействительный или отсутствующий
  `ADMIN_TOKEN` не может быть компенсирован успешным Access JWT.
- Не оставлять незащищённый `/health` на том же origin/порту в remote mode.
  Локальный startup/readiness check следует отделить от remote HTTP
  маршрутов безопасным приватным каналом (предпочтительно локальный Unix
  domain socket с ограниченными правами/жизненным циклом) либо иным
  listener, гарантированно не включаемым ни в один tunnel ingress.
  Нельзя делать исключение по loopback IP на общем публично достижимом
  listener: иной ingress может доставить запрос к нему локально. Если
  отдельный канал не реализован, `/health` тоже требует Access JWT; это
  не основание пропускать unauthenticated health через ASGI middleware.
- Прямой запрос по другому named tunnel к тому же ASGI-приложению обязан
  пройти тот же JWT/issuer/audience/email gate, независимо от proxy.
  Клиент может принести корректный подписанный JWT напрямую — это допустимо
  только как аутентифицированный запрос по указанным условиям, но само по
  себе не доказывает разрешённый tunnel. Если политика проекта требует
  единственный ingress, её enforcement относится к отдельной полной проверке
  конфигурации из предыдущего ТЗ.

### 9.4. Извлечение и валидация Cloudflare Access assertion

1. Источник Access assertion для origin — HTTP-заголовок
   `Cf-Access-Jwt-Assertion`, согласно официальной документации Cloudflare:
   <https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/>.
   Cookie `CF_Authorization` не гарантирована и не является обязательным
   условием: её отсутствие не влияет на решение, если header assertion
   присутствует и полностью валиден. Cookie не использовать как fallback или
   независимое доказательство. Не принимать значение из `Authorization` как
   Access-токен: этот заголовок сохраняет контракт `Bearer ADMIN_TOKEN`. Не
   доверять `Cf-Access-Authenticated-User-Email` или иным непроверенным
   identity headers как доказательству личности.
2. Не принимать пустое значение, malformed JWT, дублирующийся/многозначный
   `Cf-Access-Jwt-Assertion` header или неподдерживаемый тип/формат.
   Принимать только один однозначный header assertion и проверять его
   независимо от наличия, отсутствия или содержимого cookie. Отсутствующий
   или невалидный header assertion означает отказ, даже если cookie есть;
   отсутствие cookie само по себе не означает отказ при валидном header.
3. Проверять JWT библиотекой с поддерживаемой криптографией; не писать
   криптографические примитивы вручную. Для согласованного Cloudflare Access
   формата принимать только `RS256` (не `none`, MAC/HMAC и другие алгоритмы),
   не использовать `jku`/`x5u` из токена или алгоритм, выбранный токеном без
   фиксированной проверки. Проверять `kid`, соответствие ключа алгоритму и
   назначению, подпись целиком и отказ при неоднозначном ключе. Не считать
   decode/base64/наличие JWT или Cloudflare identity header проверкой подписи.
4. Ожидаемые `issuer` и `audience` задаются доверенной локальной конфигурацией
   конкретного Cloudflare Access application и не извлекаются как источник
   доверия из предъявленного токена. Проверять обязательный `iss` на точное
   совпадение с issuer команды Cloudflare Access и `aud` на точное совпадение
   с AUD целевого Access application. Отсутствие, неверный тип,
   лишние/неожиданные значения или несовпадение ведут к отказу. Формат
   проверки определяется документированным Cloudflare assertion; конкретные
   team domain, issuer и AUD должны быть заданы для выбранной установки и
   проверены до remote запуска, но не считаются известными или настроенными
   в текущем проекте.
5. Источник доверия для issuer/JWKS — выбранная владельцем команда
   Cloudflare Zero Trust/Access и созданное в ней конкретное приложение.
   Подтверждённый стандартный формат: issuer команды вида
   `https://<team>.cloudflareaccess.com`; подписывающие ключи RS256 получают
   по HTTPS с `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`,
   выбирая ключ по `kid`. Для ротации ключей обновлять доверенный набор с
   сохранением проверки подписи; неизвестный `kid` требует ограниченного
   обновления ключей, а не обхода проверки. Значение `<team>` и AUD
   приложения задаются для выбранной установки. Это описание формата не
   подтверждает существование аккаунта, конкретного приложения или
   настроенности значений в данном проекте. Не получать issuer/JWKS URL из
   неподтверждённого JWT, произвольного `Host` или клиентского запроса.
   Endpoint строить только из закреплённого team domain по HTTPS; не
   допускать SSRF, произвольных redirects или подмены trust root.
6. Проверять `exp` как обязательный корректный числовой claim и отказывать
   после истечения с минимальным явно ограниченным clock skew. Если `nbf`
   присутствует, он должен быть корректным числовым claim и токен не может
   использоваться до его наступления (с тем же ограниченным skew).
   Для конфигурации, где официальный Access assertion гарантирует `nbf`,
   требовать его обязательное наличие; это условие должно быть подтверждено
   тестовыми/официальными примерами до включения. Отклонять malformed,
   отсутствующие обязательные claims, `exp <= nbf`, чрезмерный срок действия
   сверх согласованного лимита, неверный issuer/audience, неподдерживаемый
   subject/claim shape и невалидные временные значения. Часы тестов должны
   подменяться; пограничные случаи тестируются.
7. Требовать `email` из проверенного, подписанного JWT claim и сверять именно
   это значение с отдельным локально заданным allowlist. Не использовать
   непроверенный identity header, cookie или клиентские данные как источник
   email. Allowlist — явная непустая конфигурация владельца, не создаётся
   автоматически из первого входа, Access header, JWKS или содержимого
   токена. Нормализация адреса должна быть определена (минимум trim и
   case-insensitive сравнение в согласованной форме); сравнение точное, без
   wildcard/доменного суффикса/подстроки. Отсутствующий, некорректный или
   неразрешённый email ведёт к отказу. Не вводить дополнительные claims как
   обязательные без отдельного подтверждённого требования.
8. Ошибки parsing/crypto/config/network/cache приводят к закрытому отказу,
   без доверия к ранее распарсенной identity или обходному legacy auth.
   Ответы отказа не должны раскрывать секреты, token, email allowlist,
   содержимое JWT/JWKS или детали внутренних путей в клиенте и логах.
   Логировать только безопасную категорию/корреляционный идентификатор без
   токена, cookie, `ADMIN_TOKEN` и секретных тел ответа.

### 9.5. JWKS cache, сеть и ротация ключей

- JWKS загружается только с зафиксированного HTTPS endpoint доверенного team
  domain, с проверкой TLS, ограниченными timeout/размером ответа и
  безопасным JSON parsing. Не следовать cross-origin redirect; ошибки,
  некорректный ответ, неизвестная структура/алгоритм/дубликаты `kid` не
  должны расширять набор доверенных ключей.
- Разрешён ограниченный in-memory cache только для JWKS, успешно полученного
  по доверенному endpoint. Задать максимальный срок свежести и отдельный
  hard maximum возраста; устаревший за пределами него cache не является
  fallback. При свежем cache и известном `kid` допускается локальная
  проверка; при неизвестном `kid` инициировать ограниченное обновление и
  принять ключ только после успешной проверки нового набора. Если обновление
  недоступно/невалидно либо `kid` после обновления отсутствует — отказ.
- Ротация должна поддерживать перекрытие старого/нового валидных ключей,
  опубликованное Cloudflare, без отключения signature checking. Не
  использовать «последний ключ любой ценой», не выбирать ключ по одному
  только совпадающему алгоритму, не принимать JWT при невозможности
  проверить подпись. При сетевой ошибке известный ключ допустим только в
  пределах заранее утверждённого свежего cache TTL; по истечении — deny.
- Не считать доступность JWKS, существование ключа или валидный JWT
  подтверждением Access policy. Нужен отдельный критерий тестов для сетевой
  ошибки, истечения cache, неизвестного `kid`, ротации, повторяющихся ключей,
  неверной подписи, смены endpoint/issuer и восстановления после отказа.

### 9.6. Первичная настройка, секреты и процессы

- Первый remote setup явно просит владельца самостоятельно выбрать/создать
  Cloudflare account/team, подконтрольный домен, Access application/IdP/MFA,
  точный hostname/audience/issuer, named tunnel и явную политику, а также
  определить разрешённых email. Лаунчер может дать пошаговые инструкции и
  проверить синтаксис локальных значений; он не должен утверждать, что
  аккаунт, домен, права владения, политика или маршрут подтверждены, если
  не проведена отдельная авторитетная проверка. Remote mode не запускается
  при незаданном allowlist, неизвестном issuer/audience/JWKS или отсутствии
  нужного tunnel setup.
- Отдельно запросить согласие на обработку Cloudflare трафика и сообщить,
  что Cloudflare находится в пути HTTPS-запросов; credential/Access token
  не подтверждают владение аккаунтом и могут быть отозваны/скомпрометированы.
  Политика MFA, персональные email и ответственность за домен принадлежат
  оператору. Наличие локального JWT allowlist ограничивает origin, но не
  гарантирует настройку Cloudflare policy.
- Tunnel credential — секрет. Предпочитать защищённое хранилище ОС (на
  macOS, если применимо, Keychain) либо отдельный файл credentials с правами
  только владельца и ограниченным доступом; точный способ должен быть
  проверен для выбранной версии cloudflared. Не записывать секрет в
  `.env.example`, HTML, SQLite, конфигурацию проекта, отчёт или тестовую
  фикстуру. Не передавать секрет в argv/командной строке, URL, stdout/stderr,
  логи, traceback, сообщения об ошибке или shell history. Разрешённые способы
  передачи (защищённый файл, stdin/FD или безопасный API конкретного
  cloudflared) должны быть подтверждены испытанием; если инструмент требует
  секрет в argv и нет безопасного альтернативного способа — запуск
  блокируется, а не понижается защита.
- Приватные файлы создаются атомарно с ограниченными правами; отказ/прерывание
  ввода не должен оставлять частично записанный credential или печатать его.
  Маскировать секреты и отказываться от включения чувствительных значений в
  диагностический snapshot. Не читать и не изменять существующие реальные
  `.env`, базы или сервисы для тестирования/первичной разработки.
- Проверять конфликты локальных портов до запуска. Не завершать процессы,
  которыми лаунчер не владеет; при занятом порте остановиться и сообщить
  безопасную диагностику. Отслеживать только собственные процессы admin,
  bot, proxy (если он дополнительно нужен) и cloudflared; при ошибке старта,
  аварии, timeout, Ctrl+C/SIGTERM либо закрытии оболочки закрыть путь
  публикации и выполнить ограниченное graceful termination, затем kill
  только принадлежащих лаунчеру дочерних процессов при необходимости,
  дождаться их завершения и reap. Повторный запуск не должен оставлять
  дочерний tunnel/proxy или ложную ссылку.
- Если ASGI middleware является обязательной защитой origin, отдельный proxy
  не может быть единственным компонентом, обеспечивающим JWT enforcement.
  Он может остаться сетевым слоем, но его пропуск/обход не отменяет проверку
  в приложении. Гарантия «только один tunnel/только один маршрут» остаётся
  условием предыдущего ТЗ о полном анализе Cloudflare policy/ingress.

### 9.7. Затрагиваемые модули и модели

Планируемые изменения при будущей реализации (это не утверждение о текущем
коде):

- `app/admin.py`: удалённый режим и ASGI middleware перед всеми маршрутами;
  без изменения бизнес-моделей и без ослабления `authorize()`.
- `app/security.py` либо отдельный модуль: извлечение assertion, строгая
  валидация JWT/JWKS, policy-free локальный email allowlist и безопасные
  исключения. Отделить чистую проверку от IO для тестирования.
- `app/config.py`: типизированные параметры режима, issuer, audience,
  allowlist и cache policy. Имена переменных, источник/права хранения и
  миграция конфигурации — проектное решение, они не существуют сейчас.
- `app/launcher.py`, `start.command`: защищённый first-run ввод и запуск,
  приватный локальный readiness канал, управление только своими процессами
  и запрет remote startup при недоказанных prerequisite. Не печатать секреты.
- `requirements.txt`: только при необходимости библиотека JWT/JWK с
  поддерживаемой версией; не внедрять криптографию самостоятельно.
- Новые изолированные `unittest`-сценарии; существующие тесты локального
  режима сохранить. Обновить соответствующую документацию запуска без
  заявления, что конфигурация Access создана/проверена автоматически.

Логически конфигурация состоит из режима (`local`/`remote`), ожидаемого
issuer, одного ожидаемого audience, непустого локального набора разрешённых
email, ограничений clock skew/JWKS cache и источника защищённого tunnel
credential. Это проектируемые значения, а не публичная HTTP-модель и не
существующие поля `Settings`. Секреты не включать в dataclass repr,
snapshot, exception, JSON API или отчет. Необходимые форматы claims и
переменных окружения фиксировать только после проверки реального
документированного Cloudflare профиля.

### 9.8. Конкретные критерии приёмки

1. В local mode сохраняется прежний запуск и его ожидаемые `/health`,
   `/admin`, CSS и API; JWT не требуется. В remote mode отсутствие/ошибка
   обязательных параметров, пустой allowlist либо ошибка загрузки доверенных
   ключей не допускают старта с ослабленной защитой.
2. В remote mode без валидного assertion ответы на `/admin`, CSS, `/health`,
   API, неизвестный путь и любой HTTP method закрыты до выполнения handler;
   то же относится к прямому доступу по loopback/другому ingress. Успешный
   токен не должен обходить существующий `ADMIN_TOKEN` на API. Внешний
   health не становится публичным; внутренний readiness канал не включён в
   tunnel маршруты.
3. Успешное прохождение требует криптографически корректную RS256-подпись
   ключом с совпадающим `kid` из доверенного JWKS с
   `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, точные `iss`
   команды и `aud` конкретного Access application, действительный `exp`,
   корректный `nbf` (и его наличие там, где это подтверждено обязательным
   claim), а также `email` из подписанного JWT claim, совпадающий с отдельным
   allowlist. Неопределённые правила claim shape блокируют запуск, а не
   получают permissive default. Ротация `kid` проходит только после
   успешного получения/проверки доверенного нового набора ключей.
4. Каждый негативный случай — отсутствующий/пустой/невалидный assertion
   header, поддельный/повреждённый JWT, неверная подпись/issuer/audience/
   время/email, неподдерживаемый алгоритм, отсутствующий ключ, malformed
   JWKS, сетевой timeout, истёкший cache и неизвестный `kid` после refresh —
   приводит к отказу без альтернативного пути. Отсутствие cookie при валидном
   header assertion обязательно проходит Access-проверку; отсутствие header
   приводит к отказу даже при наличии cookie. Cookie не является требованием,
   fallback или параллельным источником авторизации. Outage за допустимым
   cache TTL закрывает remote доступ.
5. Identity headers, `Host`, forwarded заголовки, cookie и `Authorization`
   не могут подменить проверенный Access identity/email. Отсутствие или
   отличие cookie не меняет результат проверки валидного header assertion.
   Валидная Access identity плюс отсутствующий/неверный `ADMIN_TOKEN` не
   выполняет защищённый API endpoint.
6. В argv, логах, stdout/stderr, traceback, UI, адресе, тестовом отчёте и
   Graphify артефактах нет токена, приватного ключа, tunnel credential,
   `ADMIN_TOKEN` или полного assertion. Утечка синтетического тестового
   значения в тестовых ошибках тоже считается провалом.
7. Тестами доказано, что падение/сигнал завершает только собственные
   процессы, закрывает публикацию и не убивает чужой listener; порт-конфликт
   не создаёт вторую публикацию и не принимается за readiness. После остановки
   дочерние процессы завершены/reap и новая ссылка не выдаётся.
8. **Отдельный release blocker: эффективная Cloudflare Access policy не
   проверена авторитетно.** Успешная проверка JWT, `kid`/JWKS endpoint,
   локальной конфигурации, ручной настройки или доступности tunnel не
   подтверждает текущую эффективную Access policy. Пока не выполнен критерий
   6.3 предыдущего ТЗ — авторитетная проверка всей действующей policy,
   hostname, bypass/конфликтов и tunnel ingress — remote запуск и выдача
   публичной ссылки блокируются. Установка не называется проверенной или
   подтверждённой. Отдельно документируется, что JWT-проверка не доказывает
   Cloudflare account ownership, корректность всех hostname/path, отсутствие
   обходов или уникальность маршрута.
9. Не выполняются production-публикация, реальный запрос к Cloudflare API,
   реальное создание/перенастройка named tunnel и реальные сервисные тесты.
   Приёмка security логики проводится синтетически локально.

### 9.9. Изолированные тестовые сценарии

- Сгенерировать ephemeral тестовую пару ключей в памяти/временном каталоге;
  выдавать синтетические JWT и мокать HTTP/JWKS транспорт, часы и cache.
  Не использовать реальные токены, `.env`, database, Cloudflare account,
  DNS, tunnel, Telegram, AI provider или работающие сервисы.
- Позитивные: валидный RS256 assertion в `Cf-Access-Jwt-Assertion` без
  cookie; тот же валидный header с отсутствующей, посторонней или не
  совпадающей cookie не отвергается из-за cookie; разрешённый `email` из
  подписанного claim; точные issuer и AUD; срок на границах `exp`/`nbf`;
  известный ключ в свежем cache; ротация на опубликованный ключ с новым
  `kid`; доступ к UI/CSS после Access при этом API требует верный
  `ADMIN_TOKEN`.
- Негативные: все endpoints/пути/методы без assertion header и с неверной
  подписью; отсутствующий header при наличии cookie; пустой, malformed или
  дублированный header; поддельный email header и email в неподписанных
  источниках не влияют на allowlist; отсутствующие/неверные claims; неверные
  issuer/audience; `exp` истёк, `nbf` в будущем, malformed времена;
  неразрешённый email в подписанном claim; смена alg, `none`, неподдерживаемый
  key type, отсутствующий/неизвестный `kid` после обновления JWKS, duplicate
  `kid`, неверная подпись. Cookie сама по себе не даёт доступ и её отсутствие
  при валидном header не является негативным случаем.
- JWKS: timeout, TLS/HTTP ошибка, слишком большой/повреждённый ответ,
  redirect на другой host, отсутствие/невалидность ключа, cache expired,
  refresh failure при неизвестном `kid`, ротация старого и нового ключа,
  hard-expiry при outage. Ни один failure не проходит по stale/alternate
  token.
- Режимы и обходы: прямой запрос к ASGI без proxy, запрос через смоделированный
  другой tunnel/ingress, запрос с поддельными forwarded headers, попытка
  пройти по `/health`, CSS, OPTIONS и неизвестному пути; remote gate не
  пропускает их без JWT. Проверить локальный health через отдельный
  приватный канал или требование JWT на общем listener.
- Лаунчер: безопасный ввод без echo, отказ/прерывание, файлы с restrictive
  permissions, отсутствие секрета в argv/logs, занят порт, неожиданный выход
  дочернего процесса, сигнал/timeout и подтверждение завершения только своих
  процессов.
- После изменений выполнить существующий стандартный test suite в
  изоляции и новые auth-тесты; записать реальные команды и результаты.
  Cloudflare live integration не требуется и не симулируется заявлением об
  успешной проверке реальной policy.

### 9.10. Риски и открытые решения

1. Формат header `Cf-Access-Jwt-Assertion`, RS256, поиск ключей по `kid` на
   `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, issuer team и
   application AUD подтверждены официальной документацией Cloudflare,
   указанной в 9.4. Для конкретного владельца всё ещё требуется установить
   его team domain, issuer и AUD выбранного приложения и проверить
   соответствие этой конфигурации; это не подтверждает эффективную Access
   policy или факт установки. Cookie не гарантирована и не является
   prerequisite для валидного header assertion.
2. Выбрать JWT/JWK библиотеку и проверить поддержку algorithm/key type,
   ограничение размера/времени, clock skew, cache и отсутствие опасной
   автоматической загрузки URL из JWT.
3. Определить конфигурацию/права для email allowlist и ротации; кто может
   добавлять/удалять администраторов, как отзываются сессии, какое окно
   действия JWKS cache и JWT допускается.
4. Проверить на синтетических тестах, что allowlist сравнивается только с
   `email` из валидированного подписанного assertion, а непроверенные
   identity headers и cookie не могут заменить этот claim. Не вводить
   дополнительные claims как обязательные без отдельного подтверждённого
   требования.
5. Выбрать private readiness transport совместимый с существующим
   `uvicorn --fd` и поддерживаемой платформой. Нельзя ослаблять проверку
   общего origin ради startup probe.
6. Установить фактическую версию/способ запуска cloudflared и доказать
   безопасную передачу named-tunnel credential без argv/log exposure.
   Account ownership, права токена и настройки Cloudflare невозможно
   удостоверить только локальной строкой конфигурации.
7. Выяснить, должен ли remote запуск оставаться запрещённым до готовности
   отдельной полной проверки Cloudflare policy из предыдущего ТЗ. По
   умолчанию действует запрет; одной JWT проверки недостаточно.
